# OpenTrack-FineTuning 设计预案

本文档对应 Open Track 中最复杂的部分：微调。

当前阶段不直接实施，只建立一个明确且合规的技术路线图，避免后续临时拼凑。

## 1. 设计定位

微调必须放在最后做，前提是：

1. 主赛道版本已稳定
2. OpenTrack-Easy 至少有一版清晰可复现的增强
3. 已经积累了可分析、可筛选的轨迹数据

微调目标不是“泛泛提升模型能力”，而是学习本项目特有的行为：

- 更好的 query reformulation
- 更少的重复搜索
- 更合理的全文展开
- 更稳的停止时机
- 更干净的最终回答格式

## 2. 数据来源原则

必须严格遵守课程约束。

允许的数据来源：

- 自己运行 agent 生成的轨迹
- 非测试集来源的开发任务或自建问题
- 课程允许范围内的自采样本

不允许的数据来源：

- `public-test`
- `private-test`
- 任何直接使用测试答案构造的监督样本

## 3. 训练路线建议

建议采用两阶段路线。

### 3.1 第一阶段：SFT

目标：

- 学会更像“研究 agent”地行动
- 学会更稳定地产生查询、展开文档、给出答案

训练对象可以是：

- 下一步动作决策
- 查询改写
- 最终答案格式

### 3.2 第二阶段：可选 RL

前提：

- SFT 后已有稳定收益
- 有足够计算资源
- 有清晰 reward 设计

否则不建议贸然上 RL。

## 4. SFT 样本设计

最合理的做法不是直接拿“问题 -> 最终答案”训练，而是把轨迹拆成行为样本。

可考虑的样本类型：

1. 动作决策样本
- 输入：问题 + 当前状态摘要
- 输出：下一步动作

2. 查询改写样本
- 输入：原问题 + 当前失败搜索历史
- 输出：更好的下一条 query

3. 文档展开样本
- 输入：搜索结果摘要
- 输出：应该打开哪个 docid

4. 最终回答样本
- 输入：证据摘要
- 输出：规范格式的最终答案

## 5. 数据筛选原则

训练数据不能全收，必须筛。

优先保留：

- 最终回答正确的轨迹
- 搜索步数较少但效果好的轨迹
- 明显体现“改写查询后找到答案”的轨迹
- 证据链清晰的轨迹

谨慎使用：

- 虽然答对但过程很混乱的轨迹
- 工具调用过多、重复严重的轨迹

## 6. RL 的最低可行方向

如果后续真的做 RL，建议只围绕简单 reward 设计：

1. 答案是否正确
2. 工具调用是否过多
3. 是否重复搜索
4. 是否在证据不足时过早停止

总体上应让模型学会：

- 更少但更有效的搜索
- 更少的无效展开
- 更稳的收尾

## 7. 评测方式

微调版本必须和前序版本逐级对照。

对照组至少包括：

1. 单步 baseline
2. BaseDemand 多轮版本
3. OpenTrack-Easy 增强版本
4. 微调版本

比较维度：

- 准确率
- 平均工具调用次数
- 平均展开文档数
- 失败样例类型
- 最终答案格式稳定性

## 8. 工程安排建议

微调阶段全部在云端完成。

云端负责：

- 训练数据存储
- checkpoint 保存
- 训练日志
- 训练后部署
- 再评测

本地负责：

- 查看结果
- 对比实验
- 记录结论
- 更新文档

## 9. 当前结论

当前阶段对微调最准确的定位是：

- 它是最后一环
- 它依赖前面版本产出的高质量轨迹
- 它必须围绕 agent 行为优化，而不是盲目追求“大模型训练”

在真正开始实施前，本文件保持路线图级别即可，不继续细化到训练脚本和超参数。
