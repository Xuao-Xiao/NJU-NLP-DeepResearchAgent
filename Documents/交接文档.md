## 1. 当前结论

### 1.1 当前 BaseDemand 已经完成了什么

当前版本已经完成课程要求中的三项基础能力：

1. 多轮检索 loop + 显式停止条件
- 不再是单步 `search -> answer`
- 已支持 `search / get_document / finish`
- 有最大轮数、无新信息、候选答案存在时的停止逻辑

2. 上下文管理
- 已从“直接堆历史消息”升级为结构化 `state`
- 已分离：
  - `search_evidence`
  - `opened_passages`
  - `confirmed_facts`
  - `candidate_answers`

3. Prompt 设计
- 已分成：
  - 问题拆解
  - 动作决策
  - 最终答案选择
  - 答案修复

### 1.2 当前 BaseDemand 还没有彻底解决什么

虽然基础结构已经具备，但性能瓶颈仍然存在：

- 复杂多跳题的实体链定位仍不稳
- 停止条件仍偏保守
- 错误文档簇早期排除不够快
- 终答虽然比之前更受控，但仍依赖证据抽取质量

结论：
- 当前 BaseDemand 已可作为“结构正确、可继续对照优化”的基线
- 但不应再把时间大量投入到低收益的小修小补上
- 后续最应该把增益押在 OpenTrack 的能力增强上

## 2. BaseDemand 迭代复盘

### 阶段 0：单步 baseline

特征：
- 单轮 `search -> answer`

已知表现：
- `first_runs` 中约 `3/50 = 6%`

结论：
- 可作为课程最小跑通基线
- 不能满足多轮检索、上下文管理、prompt 设计的要求

### 阶段 1：第一版多轮 loop

改动方向：
- 新建 `multistep_agent`
- 引入 `search / get_document / finish`
- 加入基本 state

已知表现：
- `BaseRun0` 约 `1/50 = 2%`

问题：
- 工具调用很少
- 实际上大量题没有真正起 agent

### 阶段 2：动作 JSON + 手动执行

改动方向：
- 不再依赖模型稳定触发原生 tool calling
- 改成模型输出动作计划，代码落地执行

已知表现：
- `BaseRun0.1` 为 `0/5`

收获：
- agent 开始真的多轮工作

问题：
- planner 输出不稳定
- fallback 太多

### 阶段 3：query rewrite + passage extraction + answer repair

改动方向：
- query bundle
- 文档相关片段抽取
- final answer repair

已知表现：
- `BaseRun0.1.1` 为 `2/20 = 10%`

收获：
- 强命中题型开始能答对

问题：
- query 污染
- 复杂题仍然不会走实体链

### 阶段 4：question decomposition + 半确定性搜证

改动方向：
- 问题先拆解
- search 后优先开文档
- 状态摘要加入 answer type 与 planned queries

已知表现：
- `BaseRun0.1.2` 为 `1/10 = 10%`
- `BaseRun0.1.3` 为 `1/10 = 10%`
- `BaseRun0.1.3_50` 为 `3/50 = 6%`

结论：
- BaseDemand 的结构已经立住
- 但仅靠 loop/state/prompt 本身，难再显著拉高复杂题性能

## 3. 对当前定版的判断

### 3.1 为什么现在应视为 BaseDemand 阶段性完成

因为课程要求的三点已经都被工程化实现：

- loop 是真的多轮
- context 不是简单堆历史
- prompt 不是一两句口头说明，而是分阶段强约束

所以从“是否完成 BaseDemand”看，答案是：
- 已完成

但从“是否已经做到成绩足够高”看，答案是：
- 还没有

### 3.2 为什么后续重点不该继续死磕 BaseDemand 微调

原因很清楚：
- 前几轮迭代已经证明，继续在同一单 agent 框架内堆更多 prompt 和 fallback，收益递减明显。
- 当前缺的不是“再多一点 loop”，而是：
  - 更强的候选验证
  - 更细的文档内定位
  - 更明确的角色分工

这正对应 OpenTrack-Easy 的两个方向。

## 4. OpenTrack-Easy 直接起步方案

### 4.1 工具增强

优先顺序：

1. `verify_claim`
- 作用：判断候选答案是否真的被当前证据支持

2. `find_in_document`
- 作用：在已知 `docid` 中定位与 query 相关的片段

3. `decompose_question`
- 作用：把复杂问题拆成实体识别、关系验证、最终字段抽取三个层次

4. `extract_answer_candidates`
- 作用：把候选答案抽取正式工具化

这些工具的核心目标不是“工具越多越好”，而是让 agent 从：
- “会搜”
变成
- “会验证”

### 4.2 多 Agent 架构

推荐最小结构：

`Planner Agent`
- 负责拆题和给出检索计划

`Executor Agent`
- 负责 `search / get_document / find_in_document`

`Verifier Agent`
- 负责判断证据是否足够支撑最终答案

推荐原因：
- 当前 BaseDemand 最大问题正是“证据闭环不稳”
- verifier 角色比额外加搜索角色更有现实增益

## 5. 下一位接手者的建议工作顺序

### 5.1 如果目标是继续冲成绩

推荐顺序：

1. 以当前 [agent/multistep_agent.py](/D:/nju-nlp-deep-research/agent/multistep_agent.py:1) 为固定基线
2. 先实现 `verify_claim`
3. 再实现 `find_in_document`
4. 再决定是否拆成 `Planner + Executor + Verifier`

### 5.2 如果目标是回头继续补 BaseDemand

只建议补这三类：

1. 更稳的字段抽取式终答
2. 更强的文档源类型识别与排序
3. 更明确的“证据足够则提前停止”

不建议再做的方向：
- 单纯提高 `max_rounds`
- 再加更多 prompt 文案
- 再堆更多 fallback 规则

## 6. 最终交接判断

当前项目状态可以概括为：

- BaseDemand：结构上已完成，性能上已证明有上限
- OpenTrack-Easy：是下一阶段最合理的突破口

因此，交接后的正确心态不是：
- “继续在 BaseDemand 上小修小补，期待突然大涨”

而应该是：
- “把当前 BaseDemand 当作稳定底座，在工具增强和 verifier 架构上寻求下一阶段提升”
